# 修复实录（fixlog）

> 从根 README 迁出（2026-10-26 整理）。这里是**事故复盘档案**：每条保留"根因 +
> 修法 + 为什么这样修"，供排障时对照与决策援引。发布说明看 `git log`，
> 这里不删条目——写过的坑就是下次的判例。

1. **state.json 数据不一致** - running 状态清理 stoppedAt 字段
2. **Cookie 安全配置** - 添加 SameSite=strict 标志
3. **管理员提权持久化** - 写入 data/config/admin.json
4. **全局错误处理** - 添加 unhandledRejection 和 uncaughtException 处理
5. **局域网 HTTP 访问 DSH Web UI** - 前端"进入 DSH"链接硬编码 127.0.0.1 已改为动态 host；`crypto.randomUUID is not a function` 已通过镜像内 polyfill 注入解决（详见 [docs/crypto-randomuuid.md](docs/crypto-randomuuid.md)）
6. **管理端破坏性操作可被 cookie 重放** - 网关转发 `admin_session` 导致提权链；已加"当场钱包签名"（见上方安全特性 6）。仅凭 cookie 现在返回 `SIGNATURE_REQUIRED`
7. **启动时 tenant patch 漂移** - 改 `server.publicHost` 后旧 `trustedHosts` 残留致 `/api/directoryPicker/list` 403；已加启动自愈 + 重启必刷新 patch
8. **网关把浏览器的失效 `dsh-auth-*` cookie 转发给容器** - 浏览器残留旧 cookie 时平台跳过注入，DSH 回 `dsh web authentication required`；已改为「平台现换的那份永远权威，旧 cookie 一律剔除」（HTTP 与 WebSocket 升级两处）
9. **「版本更新」因备份目录默认值必然失败** - 内置默认 `backupDir` 是 `/backup/dsh-multitenant`，普通用户直接跑平台时无权创建 → 备份 EPERM → 更新中止（容器已停过一次白停）。默认已改为平台自有 `data/backups`；配置的目录不可写会**自动降级并告警**，且「预览」会提前报出快照目录可写性
10. **版本列表取不到（npm EPERM）** - 宿主 `~/.npm` 不可写时 `npm view` 直接失败；已为 `npm view` 显式指定可写缓存目录（`dsh.npmCacheDir`，默认 `data/npm-cache`），不再依赖运行用户的 `~/.npm`
11. **版本历史看不出镜像是否还在本地** - 同一版本可被构建多次（每次新镜像 ID，tag 只有一个 → 后来覆盖先前），历史却全部保留，容易误以为多条同版本记录都能回滚。已标出「在本地/不在本地」+ 体积 + 保留原因，并支持多选清理悬空构建（破坏性操作，需管理端签名）
12. **悬空镜像清理筛不出任何东西** - 镜像 untag 后 `docker images` 的 Repository 变成 `<none>`，按仓库名过滤会一个都筛不出来（功能失效）。已改为用平台构建历史认领归属，既能清理自己的悬空构建，也绝不会误碰别的项目的镜像
13. **清理入口在"没得清"时整个消失** - 清理区只在有可清理项时渲染，而镜像通常都带 tag → 用户看不到这个功能。已改为**始终显示**镜像清单与清理区（含"为什么不可删"与谁在用），并允许清理带 tag 的旧版本（旧 tag 一样占 1.2GB）
14. **"容器在用"判定会漏判（有误删风险）** - `docker ps --format '{{.Image}}'` 对带 tag 的容器返回**名字**、对悬空镜像返回短 ID，用名字永远匹配不上 sha256 → 该容器被漏判。已改为逐个 `inspect` 取完整镜像 ID，并让"拿不到信息"直接失败而不是猜着删
15. **镜像归属漏认自家悬空构建** - 只靠平台历史认领会漏掉"构建中途失败 / 手工 `docker build`"留下的镜像（它们从未进历史），那部分空间永远清不掉（实测有一个 843MB 的）。已补 Dockerfile 签名兜底（`DSH_HOME`/`DSH_TELEMETRY_DISABLED`/`DSH_VERSION`），只对无 tag 镜像逐个 `inspect`，认不到就不认领
16. **"当前镜像"标记永远不亮** - 平台存完整 `sha256:...`、docker 给短 ID，用 `===` 比较恒为 false。已统一用双向前缀匹配
17. **DSH 版本管理层次不清** - 版本列表 / 构建镜像 / 总体镜像 / 租户镜像混在两三个卡片里，看不出递进关系，且"本地手上已有哪些版本"无处可查（`stable` 还恒为空，因为该包目前只有预发布）。已重排为 4 步：①本地版本列表（含已验证已构建标记）②构建版本镜像 ③总体镜像（全部租户共用）④个别租户镜像，版本下拉合并并按版本号排序
18. **租户镜像不能选（只能升到最新）** - 平台只能把租户升到 `latest`，既不能回滚到旧版本，也不能让不同租户跑不同版本。已在「个别租户镜像」加**目标镜像选择**：默认跟随最新，也可钉到任一已构建版本（`state.pinnedImage` 持久化，重建与重连都沿用；销毁中的租户也会记住选择）。安全上：镜像必须属于本平台仓库、必须能读出 DSH 版本号，且目标镜像会**签进管理签名绑定**（防"签 latest、实装别的版本"）
19. **沙箱逃生开关变量名写错（写了也不生效）** - Dockerfile 注释让运维在 bubblewrap 不可用时改用 `ENV DSH_SANDBOX_MODE=danger-full-access`，但 DSH 只认 `DSH_PERMISSION_MODE`（`DSH_SANDBOX_MODE` 在整个 DSH 包里出现 0 次）。照注释改会以为已放开沙箱，实际仍以 `workspace-write` 启动后失败。已改为正确变量名并注明副作用（`danger-full-access` 会同时把审批策略变成 `never`）
20. **租户容器缺 agent 常用工具** - 容器内实测没有 `curl`/`jq`/`ripgrep`：抓网页只能 `node -e "fetch(...)"`、解析 JSON 要写一行式、搜索只能用 `grep -r`，每次绕路都消耗 token。已在 apt 层补上这三个包（镜像仅增 ~10MB）
21. **租户列表看不到 DSH 版本** - 后端未下发版本、且「版本」列实际渲染的是状态徽章；已加 `containerDshVersion()`（问容器 `dsh --version`，按镜像 ID 缓存）并在两个列表里正确展示
22. **「重启 DSH」报 `Container ... not found`（线上实测）** - 状态漂移：容器已停止 >60min 被清理定时器销毁，而界面还停在打开状态，用户点重启时后端仍按"重启已有容器"执行 `docker restart` → 404。修法：四处 `containerInfo` 为不存在时的处理全部改为**按各自目标语义对齐**，而不是把不一致抛给用户 —— `restartContainer` 降级为启动（委托 `ensureContainer`，沿用 `pinnedImage`，重建无损）、`stopContainerForUser` 照常结算额度并返回成功（停止目标已达成）、`forceStopContainer` 对齐状态且不把 `destroyed` 覆写回 `stopped`、`upgradeContainer` 只记录 tier 待下次创建生效
23. **容器创建报 `--storage-opt is supported only for overlay over xfs with 'pquota'`（线上实测，阻断性）** - 磁盘配额参数只在特定宿主后端可用（overlay2 需 xfs+pquota；btrfs/zfs 原生）。在不支持的宿主上 Docker **直接拒绝整个 `docker run`（exit 125）**，容器根本创建不出来、租户全部进不去 —— 旧注释/`deploy/check-storage.sh` 假设的「参数被接受但不强制（软配额）」在部分 Docker 版本上不成立（本地实测 overlayfs 确实接受并记入 `HostConfig.StorageOpt`，所以本地永远复现不出来）。已改为：首次被该原因拒绝 → 去掉参数重试一次（配额降级为不限制）并记住宿主能力，后续创建直接跳过；**只对这一种明确原因降级**，其它错误照旧上抛。同时修正 `check-storage.sh` 的判定与 `--test` 分支（原先会把「驱动拒绝」误报成「软配额」）
24. **启动失败只报 `did not become ready`（线上实测，无法定位）** - 容器创建/重启成功但容器内 DSH 没就绪时，错误里只有一句「没就绪」：看不出是崩了还是没监听，也没有日志。更糟的是 `finalizeTenant` 失败会**回滚删容器**，日志随之永久消失。已加 `containerDiagnostics()`：采集 `status/exitCode/OOMKilled/内存上限` + **合并 stdout/stderr 的日志尾部**（`docker logs` 把容器 stderr 写到进程 stderr，只用 `sh()` 会丢关键行）并写进错误；且采集严格发生在回滚**之前**。同时 `waitReady` 支持 `{containerName}`：容器已退出时**立即失败**，不再白等满 120 秒
25. **保存 API Key 把 `.credentials.yaml` 写坏 → 容器再也起不来（线上阻断性）** - 平台的合并工具是「整篇解析 → 重新渲染」，把不认识的行当注释收集后**搬到文件开头**，且 refs 块结束分支缺 `continue` 导致同一行被 push 两次 → 重复键/缩进行跑到文档开头 → YAML 非法 → DSH `credentials-local` 拒绝加载 → 退出 1 → 平台只能看到「容器未能就绪」。触发条件很现实：DSH ≥0.1.5 会自己往该文件写 `client-connection/browser-session`（认证 cookie 签名密钥靠它持久化），此后用户只要在「模型配置」存一次 Key 就会写坏。已改为**原地最小编辑**（只动 refs 块内的目标条目，其余内容逐字节原位保留），并修正：键名接受 `.`/`-`、删空写 `refs: {}`、既有值规范化为字符串（裸 `123`/`null` 会被 YAML 解析成非字符串而遭 DSH 拒绝）
26. **凭据文件损坏 → 整个租户进不去（兜底自愈）** - 第 25 条修好了「不再写坏」，但已经坏掉的文件仍会让 DSH 启动即退出、用户完全进不去（数据卷其实是好的）。已加自愈：启动未就绪时采集现场，**若判据是 `credentials-local` 解析 `/dsh-home/.credentials.yaml` 失败**，就把坏文件改名为 `.credentials.yaml.broken-<时间戳>`（留档不删）并再启一次，容器便能以默认值起来；租户记录留下 `credentialsQuarantinedAt/Path`。判据取自 DSH 自己的报错（生产依赖里没有 YAML 库，DSH 的 credentials-local 才是权威），并**严格要求同时命中文件名与错误类型** —— OOM/端口占用等无关故障照旧回滚，绝不误伤用户已保存的 API Key。代价：隔离后需在「模型配置」重填 Key（平台不留存 Key 值）
27. **浏览器报 `dsh web authentication required`（本地正常，线上必现）** - 浏览器看到的是 **DSH 自己的英文提示** → 说明请求被转发进了 DSH，即平台注入了失效的 `dsh-auth` cookie。根因：DSH 的 cookie 由租户卷 `.credentials.yaml` 里的签名密钥签发，容器重建/换镜像/**凭据被自愈隔离（密钥重生成）**都会让其失效；而 `AuthCookieCache` 把 cookie 缓存 **29 天**，`clear()` 虽然写了、注释也写明「容器重建/换镜像后必须清掉」，**全仓却无一处调用** → 网关持续注入死 cookie，DSH 恒回 401。已加两道防线：① `tenantGateway.listen()`（容器就绪：新建/重启/换镜像/启动恢复）与 `close()`（容器下线）时清缓存；② 上游回 **401** 时丢缓存、重新激活并**重试一次**（仅 GET/HEAD，避免重放 POST 请求体），仍失败才透传。注意 `listen()` 内部先调 `close()`，两处清缓存互为冗余
28. **保存 Key 会把「多行折叠值」改坏（第 25 条修复自身的回归，实测真实文件才发现）** - DSH 自己写出的 API Key 值是**跨行折叠的引号标量**（`KEY: "sk-sp-AAAA` 换行 `  BBBB…"`），第 25 条为「值必须是字符串」而加的「规范化所有 refs 值」是**按单行**取值的，会把这种值截断成 `"\"sk-sp-…"` 并把续行留成孤立残行 → YAML 再次非法。已改为：只对**完整单行裸标量**补引号，跨行折叠值与已带完整引号的值一律原样保留；并且 `set`/`del` 按**条目整段**（含续行）替换/删除，不留残骸
29. **「重置容器」总是报「没有权限重置此容器」(403)，管理员却可以** - `/api/user/:addr/reset` 用了 `getSessionAddress()`，而它只读**管理员会话**（`return getAdminSession(req)`），普通用户只有 `user_session`，于是 `session` 恒为 null → `session !== address && !isAdminUser` 恒真 → 普通用户重置自己的容器**永远 403**；只有带 `admin_session` 的管理员能重置。本文件其余 6 处「本人或管理员」判定都用的 `getRequestAddress()`（= 管理员会话 ?? 用户会话），只有这里漏改。已改用 `getRequestAddress()`
30. **「启动容器」提示成功但状态仍是「已销毁」** - 前端 `restartContainer` 走 `/connect` 后**完全不检查 HTTP 状态**，容器创建失败时后端回 502（未就绪/内部错误）、202（额度用尽或排队）、503（队列满），前端一律弹「启动成功」，于是出现「提示启动了、状态却还是已销毁」——真实原因被吞掉。已改为检查 `res.ok`，失败时把后端的 `message/error` 展示出来（「进入 DSH」本来就有检查，只有这一处漏了）
31. **凭据文件被搅乱的结构继续被写入** - 实测真实损坏形态：DSH 的 `records:` 块被塞进 `refs:` 内部（`records: ""` 却带更深子级）→ DSH 完全起不来。本工具是按行编辑，遇到这种输入只能尽力而为。已加**写入前结构自检（fail closed）**：找不到顶层 refs、refs 内有重复键、单行标量条目却跟着更深子行、出现无法识别的行 → **拒绝写入并报错**，绝不二次破坏（文件保持原样）
32. **「保存 Key」写坏凭据文件的真正根因** - DSH 在没有 API Key 时写的文件是 `version: 1` + `records:`（**没有 `refs:` 块**）。而「旧扁平布局迁移」把 `records:` —— 一个**块头**（自身无值、后面跟更深子级）—— 误当成凭据条目迁进 refs，其子级随即成为 refs 下的孤儿 → 文件损坏 → DSH 起不来（容器 120s 不就绪 → 回滚 → 界面「已销毁」；保存 Key 的接口则因第 31 条的 fail-closed 自检而报「拒绝写入」）。已修：只有**值非空的顶层标量行**才算旧扁平凭据条目，块头及其子级一律原样保留。这条才是「填 Key 反而坏文件」的根因
33. **容器里所有 bash 命令报 `Error: spawn bwrap ENOENT`（本地/线上都有）** - 报错文案是**误导**：bwrap 一直好好的，真因是 **DSH 会话的默认工作目录 `/root/workspace`（= `$HOME/workspace`）在镜像里不存在**。bash 工具的沙箱以该目录作为 `spawn` 的 cwd，而 **Node 在 cwd 不存在时同样抛 ENOENT**，报错文案却是 `spawn bwrap ENOENT` —— 于是被误判成「bwrap 没装」（连 DSH 自己的提示都这么说）。本地精确复现：`spawn('bwrap', …, {cwd:'/root/workspace'})` → `ENOENT syscall=spawn bwrap`；换成存在的 `/srv` → 正常；`mkdir -p /root/workspace` 后 → 沙箱正常运行且可写。已修：镜像内置该目录（Dockerfile），平台在容器就绪后（finalizeTenant / restartContainer）再 `mkdir -p` 兜一层，老镜像建的容器也能自愈
34. **管理端刷新频率可调 + 分层轮询** - 原来前端硬编码 `setInterval(fetchData, 10000)`：切 tab 不刷新（最多滞后 10 秒）、切到后台仍空转、多管理员/多标签页各自重复打 docker（每轮约 2 秒）。已改：① 间隔改由后端下发（`config.json` 的 `admin.refreshIntervalMs`，**默认 15000**，可填 300000=5 分钟，改完只需重启服务、不必重建前端）；② 只在前台可见时轮询（后台跳过、回到前台立即补一次、切 tab 立即刷新，1 秒节流）；③ 顶栏新增全局「🔄 刷新」按钮（手动刷新带 `?force=1` 绕过服务端短缓存）；④ 服务端 `getAllUsers` 加 3 秒短 TTL 缓存（`admin.usersCacheTtlMs`）并在**任何状态写入时立即失效**，多个管理员共享一次采样；⑤ `docker stats` 改**批量一次**（N 进程 → 1）。另修一处既有测试隔离缺陷：`finalize-tenant.test.js` 用的是真实 `state.json` 且未清 `usages`，平台自己把该地址跑到当日上限后会让用例无故失败

35. **管理员会话可被"盲签"夺取（跨端点凭证混淆）** - 加固前所有入口只签一个**与用途无关的裸 nonce**，且共用同一个挑战池。于是存在一条完整攻击链：攻击者自行调用**公开无鉴权**的 `POST /api/admin/challenge {address: 管理员地址}` 领到属于管理员的 nonce（服务器主动回给他），再诱导管理员对这个没有任何语义的十六进制串签名（钱包弹窗里看不出在授权什么；平台自己的网关校验页 `tenant-proxy` 就常驻在**租户容器域**上要求签 nonce，租户完全可控 → 这条链对"管理员点开会话中的租户容器"是内建的），最后把签名交到 `POST /api/admin/login` 即得 12 小时管理员会话——**私钥全程安全，签名是管理员本人真签的**。已修：① 被签内容改为服务端构造的**用途绑定**消息 `hex(dsh-multitenant|<purpose>|<address>|<nonce>[|<binding>])`，用途是服务端常量、客户端无法影响；② 挑战池按 `用途|地址` **分池**，为 A 用途发的 nonce 在 B 用途处消费不了；③ 网关转发进租户容器前剥离 `admin_session`/`user_session`/`gw_ok`（纵深防御，租户再也偷不到那串 cookie）。hex 编码不是装饰：`@swtc/keypairs` 内部按 hex 解码消息，直接喂含 `|` 的 ASCII 会被**有损解码**（非法字符对 → NaN → 0）而产生碰撞。覆盖 login / connect / tenant-config / skills / gateway-verify / admin-op 全部签名入口。

36. **CWT 申请可被未认证洪泛刷爆磁盘/灌满审批队列** - `POST /api/user/cwt/apply` 是**未认证**端点，token 由调用方自签（零成本），而加固前 pending 申请**无任何总条数上限**、且每次入队都**全量重写** `data/cwt/applications.json`（刷 n 条是 O(n²) 写放大）——可被刷爆磁盘并灌满管理端审批队列。已加三道边界：① **token 字节上限**（`cwt.maxTokenBytes`，默认 8192，超限 413）；② **待审批队列总条数上限**（`cwt.maxPending`，默认 500，超限 503 `OVERLOAD`）——这道检查**刻意放在验签之前**，队列满时连密码学开销都不付；③ 该接口**按 IP 限流**（10 次/分钟，10 之外的请求 429）。上限用实例字段实现（便于测试注入小值，与 `data.service.recordsMaxBytes` 同一做法）。**未做**：approved 申请仍明文存 token（改存 SHA-256 摘要属存储格式迁移，需单独一轮）。

37. **seed-to-pem 打印"派生地址"是假地址（差点误判 seed/钱包错配）** - `Keypairs.deriveAddress(secret)` 把 **seed 字符串**直传给了期待**公钥 hex** 的函数：base58 字符被按 hex 有损解码（fixlog #35 同族教训，这次踩在自家工具上），得到一个**确定性但无意义**的地址并打给使用者做"配对核对"。用户实测：钱包真实地址 `jNyJLQ…`，脚本打印 `jMD4XX…`——一度看似 seed 与钱包错位的严重身份事故。排查：四变体实验证明库本体口径（`deriveAddress(deriveKeypair(seed).publicKey)`，压缩 66 hex）能完美复现钱包地址——**密钥与 PEM 全程正确**（私钥来自 deriveKeypair，PEM 有往返自证；`shelf-open` 用的是正确口径），死的只有打印行。已修：改为 `deriveAddress(bytesToHex(noble压缩公钥))` + **双源互证**（库返回的 publicKey hex 与 noble 重算不一致即中止，本次修复过程中该互证立刻抓到第二层错——noble 默认返回 Uint8Array 而非 hex，双源比对打印出 `3,93,199…` 逗号串）。教训：**凡把字符串喂给 hex/base58 解码器，非法字符不报错只静默截断**；任何"核对用"的派生值必须与权威来源（钱包 UI）对得上才算数，工具打印本身不是权威。

38. **领取凭证在局域网 http 下炸 "reading 'digest'"（非安全上下文缺口第二弹）** - `UserCenter.vue` 的文件签前置哈希用 `crypto.subtle.digest`：该 API **只在安全上下文存在**（https/localhost/127.0.0.1），浏览器经 `http://<局域网IP>:8090` 访问时 `crypto.subtle` 为 undefined。本地 127.0.0.1 永远复现不出来——与 #5/#27、`docs/crypto-randomuuid.md` 同族（那次死 randomUUID，这次死 subtle）。修复：`frontend/src/utils/sha256.js` 兜底封装。过程自纠三连值得留档：**手写 FIPS 实现连续出偏**（DataView 默认小端忘传 true → 常数表手敲 K[55] 错值 → 修完仍不对），且"拿 Math.cbrt 重算常数自证"本身不可信（浮点精度不足以校验 32 位小数常数）——**密码原语不该自造**，最终收敛为复用生产依赖 `@noble/hashes`（vite 向父级解析 node_modules，前端零新增依赖）。对拍测试（test/sha256.test.js，node 原生 crypto 为权威）4/4 过，手写版三轮全红的教训被永久钉死。判权含义：KB 级档案字节的 sha256 错一格，签出的文件签官网必验不过——兜底路径与 native 输出必须逐字节一致。

39. **三路独立审查员"仔仔细细检查"27 案——修 22、证伪 1、知情保留 4**（2831ad6/73535e8/dcc172b + 954 全绿）- 对网关雷达、环境端点群、快照/代际链做 fresh-eyes 全量读码 + 本人前端/流程自查。本册新增判例性质的条目：
    - **报错不空跑回退**：revert/submit/unpublish 收到非法 body 时 `parseJsonBody` 已回 400，处理器却拿 `|| {}` 继续跑**完整破坏性回退**——客户端见"报错"而世界已变（apply 路由本来就是对的，这三处漏同款守卫）。改 `if (!body) return true`，一处模式五处齐（另两处 envinv/envbrowse 顺手）。
    - **下架不谎报来源**：作者下架被别人用着的模板后，"别人"来源条称默认环境（实物明明跑着模板镜像）——runningTpl 改认"我同意过的账"（published / 本人所著 / pinnedBy 含本人）。inventory 探针此前**无任何过滤**，他人 draft 亦可按 imageId 匹配亮名——同一谓词收口。fromTemplate 只回 name/slug/author，不构成未上架 intro 泄露。

    - **清除清单清错世界 + 换钉即迁账**：hadTpl 取 pinnedBy 首个命中，先后套过 A/B 的人按旧账 A 的清单清除——源头改为实物 pin 所在模板（pinnedBy 只兜底）。apply 从不清旧账：A→B 后 A 的 pinnedBy 永久挂本人（usingCount 虚高、GC"被引用"护栏被撑大、清错清单的共犯）——换钉时逐户新鲜读摘除本人。pinnedBy 清理循环同步改新鲜读（陈旧覆写吞他人账，apply 侧判例同款）。
    - **重建失败不失明**：清除已执行、applyImageVersion 抛错时回执只剩"失败"——已删的东西必须上报（cleanNote 随 500 走，remove-skill 幂等、重试安全）。

40. **下架变"待审核"→ 揪出状态机幽灵字面断头案** - 用户直觉正确：产品里没有"草稿"这回事（定格直接进审核队列 `draft`，用户面从无草稿入口），下架后被冠"草稿/待审核"都属张冠李戴。根盘查发现更深一层：本系统状态字面 `draft` 的**真实语义是"已提交待审核"**（env-commit 造它、管理端过审/驳回只认它），而我上轮实现"作者下架→重新提交"闭环时发明了字面 `pending`——**管理端队列根本不收 pending**，"重新提交审核"一点，东西就从管理员视野消失（断头路）。修正：作者下架 → `unlisted`（用户面=已下架，黄牌，可重提）；重提 → 回到 `draft` 本体（管理队列真收）；`pending` 字面清零（存量本就无 pending 行）；`revoked` 从与作者下架撞名的"已下架"改牌**已撤板**（管理员裁定，作者不可自行回队）。教训：**新代码引入状态字面必须与全部消费端对表**（管理端 approve 的 `!== 'draft'` 就是消费端），发明词典里没有的词=发明孤儿态；"改名先改所有读它的眼睛"（管理端 FILTERS/badgeCls/用户区按钮 v-if 三处同步）。

41. **格完却见"默认环境"——定格必须完结账** - 用户容器定格→审批通过→我的作品有名字了，"当前环境"却还标默认。旧账本里定格只是"产出一套模板"，作者自己并不与它发生使用关系（pin 空、pinnedBy 空），探测扑母镜像、兜底无针可认——画面对，语义瞎：你格的就是你这台容器，内容一字不差，凭什么说你现在用的"不是它"。裁定：**定格=自采纳闭环**——模板入账本同时作者 pin 落这套（换钉即迁旧账，与 apply 面同款纪律）、pinnedBy 首位记名=作者；来源条按 pin 认账。尽力轨：定格主体已成功，采纳环节炸只记 `env_adopt_failed` 审计不反杀。注意 pin 的真实权重（重连按它重建），所以母镜像上继续改动后重连会回到定格点——这正是"我用的就是这套"的承诺本义，与 apply 后改动的规则一致，不是新雷。

42. **子项可选：隐私压过"快照纯洁"** - 先前论定"目录拆着选=拼图不是定格"，用户一句"子项也可能涉及隐私"推翻之：密钥躺在项目目录里时，"整棵带或整棵不带"是在逼人选泄露。裁定改立：**勾选目录=整棵随行，子项可逐个摘除**——被摘者只留本人容器、不进镜像；定格仍是"现状减去明示排除"的快照，manifest/账本/预览三处如实记排除清单（这就是它不是拼图的原因：**排除是明账，不是暗剪**）。纪律三条：①摘除清单必须恰好两段 `目录/子项`，畸形=400 响亮拒绝——隐私的失效绝不许静默；②父目录没勾则摘除项自动滤除（整棵都不带，摘除无意义，不留脏账）；③admin 代格与 user 自助同闸同格式。

43. **"卡住不动"的正主是 CLI 超时，孤儿 stage 图像是它的尸体** - 用户定格 200 秒无下文。HTTP 会话过期无法代跑，改**进程内直调 runEnvCommit 演练**：T+120s `docker commit` 被 spawnSync 的 120s 全局预算 SIGTERM——daemon 侧还在建像，CLI 死了，页面永远等。修：定格两记 commit 专列 `ENV_COMMIT_TIMEOUT_MS=10min`（可 env 覆盖）；finally 的孤儿清剿从一次 rmi 改**轮询 15×2s**（等 daemon 建完再删，实测留过一只 1.53GB stage 孤儿）。教训：**全局超时预算不能一刀切**——快操作（ls/inspect）的 2 分钟是护栏，慢操作（commit/export）的 2 分钟是绞索；预算要按操作的物理成本分层。
44. **未勾选的目录根本没被清出定格物——"默认全清"只对文件成立** - 演练产物 `ls` 顶层仍有 data/、workspace/（均未勾选）。SCRUB 用 `find -maxdepth 1 -delete`，GNU find 对**非空目录**报 "Directory not empty" 后静默跳过，末位 `'true'` 把退出码抹平——整棵未勾选目录连里面的密钥**照样烧进镜像**，用户的"全清"是假的。修：逐条目 `for e in 顶层 glob` + `case basename in 保留名单 *) rm -rf ;; esac`（含 `.[!.]*`/`..?*` 藏匿面），演练三验证：顶层只剩勾选的 研报/、其内只剩未摘除的子项。教训：**"清空"类语句必须按对象类型枚举验证**（文件/非空目录/隐藏条目三面），删除脚本的退出码被末位 true 掩盖是经典静默失败面。
45. **"到第三步直接开始定格"= 预览页没说不开始、按钮没说不点** - 向导第三步其实只做了 dryRun 预览，但页面 ①预览中措辞含糊 ②"开始定格"未勾知情时静默 disabled ③执行中文案让等待像卡死。三处措辞归位：预览中明示"还没开始定格，容器和镜像都不会动"；未勾 consent 时按钮旁给指路话；执行中把"15~60 秒"改成诚实的"数十秒，首次/大容器可到几分钟"。判例：**disabled 按钮必须自带"为什么按不动"**，静默禁点是把用户关进哑谜。

46. **驳回即弃像，钉必须跟着卸——吊空引用是断头账** - 判例41 的自采纳让作者的 pin 也指向 draft，于是"驳回删像"多了一条没接的尾巴：像物理消失、用户的 `pinnedImage` 还指着它，下次容器销毁重建就吊空炸。修：`unpinHolders(templateId)` 扫 state 卸钉+存盘+审计，驳回路必调，`pinnedBy` 账册随像作废，回执如实报"N 人的钉选已随之解绑"。**对照撤板（判例40）：撤板对象还在、不驱逐在用者；驳回对象物理消失、必卸账——两种"下架"的账尾处理相反，因为实物状态相反。**
47. **`?.()` 吞掉不存在的方法，演练垃圾当场留库** - 演练清理用 `dataService.deleteEnvironment?.(tag)`，该方法**根本不存在**，空链吞掉、脚本打印"处置完毕"，三行垃圾账留在库里等管理员来驳回。与"replace 必须断言命中数"同族判例：**清理动作必须验实物消失（读回断言），不许靠"调用没炸"当成功**。

48. **回退语义裁定 C：默认干净、当面可留、弹窗列去留** - "回退"此前只有一句"卷数据不会动"，用户无从知道技能/插件去哪了。裁定：**「一并清除」默认勾上**（回退=倾向干净是家规，想保留必须当面取消勾选——意图要用动作表达，不用默认值猜）；确认弹窗升级为**去留明细**（留：卷内配置/API key/凭据/租户注入；换：默认 DSH 版+解钉；存：工作区入回退存档；清：按模板清单卸载随行物销账）。判例：destructive 动作的弹窗不许只问"确定吗"——**必须把"什么会留下、什么会消失"逐条列给当事人看**。

49. **admin_session 整体废止，全平台一张票（user_session 单源）** - 双票制（管理 admin_session + 租户 user_session）是系列病根：残留 admin cookie 抢占凭证身份（F9 循环）、撤板签名被"同账户"闸拒、两套过期语义（12h 硬到期 vs 滑动续期）互相打架。裁定：**去除 admin_session**——`/api/admin/login` 保留但经 isAdmSync 把关后签发唯一 user_session；`getAdminSession` 收缩为 getUserSession 别名（46+ 调用点语义本就取"操作人地址"，判权在 requireAdmin/isAdmSync 不在取址）；logout 双 cookie 卫生清除；getRequestAddress 单源化。反劫持承重不变：破坏性操作 challenge 仍绑会话地址当场验签——**只偷到 cookie 没有那把钱包，照样签不出**（P0-1 墙原样）。迁移=硬切：旧 admin_session 立刻失效，浏览器需重签登录一次。教训：**同一浏览器同一人的两张票必然漂移**，身份要单源；权限（是否管理员）与会话（是谁）解耦后，判权看凭证/名册、认人看票，两不相欠。

50. **下架/撤板后作者回落默认环境——"定格完结账"的后半条去路** - 判例 41 让定格自动钉住作者，于是作者永远"住在自己定格的东西"里：模板被下架/撤板后，他重连仍回滚到那个定格点，攒的新改动随时可能被时间机器抹掉，再定格反而束手束脚。裁定：**下架与撤板都只解作者本人的钉**（pinnedImage→null，账本 pinnedBy 同步摘名），当前容器与文件分毫不动（重建保文件靠工作目录快照三件套，与 pin 无关）；**在用他人一律不驱逐**（撤板不驱逐判例原样保留）。效果：重连=默认底座+他自己攒的文件，下次定格定格的就是现在。回执诚实：`selfUnpinned` 旗 + note 明说"作者已回落默认环境（文件原封不动）"，前端 toast 尾句跟进、来源条即时改口。教训：**计数不许心算陈旧引用**——回读账本再 filter 作者，对已摘/未摘幂等；测试夹具的"另一个人"必须真·异于主角（自撞曾假摔）。

51. **用户面动词裁定：定格→上传（代格→代传，格出→传出）** - 用户拍板"上传更好一点"。范围=一切用户可见文字：zh.js 全部 31 组话术、后端错误/note/hint 19 处字符串（含 docker.service 产物异常话术）。**注释与判例正文保留"定格"**——那是账本里的历史技术词，界面动词才归当下用户。教训：**改词要连派生词族一起扫**（格出/再格/代格/纯镜像定格……只改主词会留下"格出翻版"这类孤儿话术）；测试断言不锚中文话术（本次零随迁）正是当初"断言锚结构不锚文案"的债还之日。

52. **幽灵插件案：双轨账本漂移 + 销账静默未命中 + 空缓存护栏反噬（三连环）** - 用户报 jndw 容器有"幽灵插件"。勘查实物：卷里 skills/plugins 皆空、宿主 installs.json 与 mongo skill_installs 各记一份互不相认（Aug 的 example-skill 只在文件、Oct 的 stock-advisor 只在 mongo）。案卷（audit 集合）还原作案链：Oct 28 install 走 mongo 轨 → Oct 30 回退演练 uninstall 时服务恰跑 **json 轨**：`removeInstallRecord` 在本轨查无此账 → `if (filtered.length !== list.length)` 不成立 → **一个字都不写、零告警**（回执却 removed:true）→ 回切 mongo 重启水合，旧账复活成幽灵。三层修复：①**mineView 实物对账**——账上有、卷里没有就地卸账（判例 46 的镜像面"像物理消失必卸账"）；探测区分三态：null=查不到（卷未建/docker 故障）**绝不当成没了**（fail-open），[]=查清为空可销；②**卸账跨轨清扫**——主轨查无时顺带摘除滞留文件轨的旧账，防回切复活；③**护栏避让**——末笔销账若删 key 会塌空整缓存，触发"空缓存防清库"护栏跳过 mongo 对账删除（幽灵删不掉、重启即复活）：改为**留 [] 空行**（"查过销清"本就是更诚实的账形）。实弹：重启水合幽灵复活 → 第一次 mineView `reconciled=1` → mongo 行落空 → 二次零幽灵。教训：**账本换轨必须清旧轨**；**"没找到"与"查不了"是两个世界**，静默 return 的销账等于没销；护栏防的是异常塌空，不许误伤正常清零。

53. **"我的技能"倒置为实物为主——账本降为附属信息** - 判例 52 修了"账有实物无"（幽灵销账），但架构仍立在"账本为主、实物来裁"上，用户一句"不应该以容器本身里面的东西为主吗"点破另一半：**卷里有、账上没记**的实物（用户在容器里手写的 SKILL.md）照样隐身。倒置：**卷内实物名单就是底账**，宿主账本降级为附属信息 join（安装日期/可更新对比）；卷里有账上没记的显示 `source:'volume'`（"容器实物在册，宿主账本没记它的安装流水"），**不自动补记**（账是账、物是物，实物不靠记账存在）。探测三态保持：null=查不了→退回账本视图并标 `unverified`（"可能滞后于容器"，诚实示弱）；[]=查清为空→干净空列表。教训：**修漂移要修成"以实物为底"的结构，而不是给"以账为主"打补丁**——单向对账只治一半的病；另：splice 函数区要**花括号配平**定位，头尾锚点会误杀区间内全部方法（本轮自伤 30 案发现场，git 回滚重建零损失）。

54. **内容级实物对账：一切"有无/新旧"的断言以卷中实物为准** - 判例 53 倒置了名单层（实物为底账），用户补全裁定："**如果两者有差异，以容器实际为主**"——把断言层也拉到实物：①市场列表的"已安装"徽标改认**卷内实物名单**（账本仅探测失败时兜底）——账上没记、卷里真有的手写技能从此在市场上也亮 installed；②`hasUpdate` 不再比"安装那刻记的哈希"，改比**卷里此刻的字节**与"货架当前版应有的安装哈希"（含 P0-4 disable-model-invocation 改写，与 install 落盘变换同型）——**用户手改文件、仓库升版，一律现形**；实物查不了（旧脚本无哈希）自动降级账本对比，不装知道。list-skills.mjs 升级为随名单输出每项 sha256（小文件哈希成本可忽略）。实弹三连（jndw 卷）：手写实物显示 source=volume/hasUpdate=true → 复制货架原样仍 true（正确：那不是"应有安装版"，P0-4 改写差）→ 写成应有安装版 hasUpdate 翻 false，收敛。教训：**"以实物为主"要贯穿到每一个布尔断言**——名单对上了，哈希口径还挂在账上就是半吊子倒置；降级路径必须显式存在（查不了≠没差异，也≠没实物）。

55. **插件出身三分（GitHub/官网/自写）→ 删护内容 + 出身自述** - 用户点破现状盲区：卷里的插件可能是作者手写的、也可能从 GitHub/官网搬的——**落卷后字节无别，出身隐形**。系统里出身唯一真咬人处=**删除权**：回退「一并清除」曾按名无差别 rm，用户自装同名件会被平台代删（误伤）。裁定 A+B：**A 删护内容**——manifest 本就逐文件记 sha256（「我当初放的字节指纹」），清扫前挂卷只读探针 env-probe-plugins.mjs 逐字节核对：全等才删；不等=槽位已被别的来源占据→留物留话如实回执；**查不了（探针 null）=不代删**（可重试），绝不猜；包内无指纹在册的名字退回旧规删但注明。实弹双向验证：差一个换行判 false、全等判 true。**B 出身自述**——上传向导每插件可声明 self/github/official/other+链接，normEnvProvenance 只收随行点名过的名字（没勾=没资格声明）、kind 枚举、url≤200、self 不配 url；审核面/货架详情展示。**声明不是防线是情报**：搬运他人代码照样受审，作者署名责任不因自述减轻。教训：**无账之物的处置权只能建立在字节证据上**——名字是槽位不是所有权；数据早就躺在包里（manifest sha256），缺的是「删除前看一眼」的纪律。技能面（有账）同理可用 installedHash 护删，列为续账；另记本轮自新教训：fixlog 未写就声称已写，消息与实物不符即账实两讫破功——补 commit 纠正。

56. **随行包内容寻址去重（CAS）+ 顺刀收掉审计扫描假绿** - 用户裁定：多用户上传带同一插件，宿主盘不能存多份。以账本现成的逐文件 sha256 为地址建 `data/env-blobs/<前2位>/<余62位>` 字节库：导出时 tar 收编入库、**同名即同内容（哈希自证后才 rename）**，重复上传=去重命中弃本地拷贝；verify/install/scan 全部先装配实物现场再作业——装包从 /blobs 只读挂点按 plan 取字节、落位前逐块复验（去重不降防：一块字节坏，引用它的每本账都验不过）。清扫立两条纪律：`removeBundle` 后拆账即销（sweepBlobs 以 environments 账本为唯一引用权威，**查账失败=本轮不清扫**，宁可留孤儿不瞎删）；被引用之物不可物理删照旧。实弹：存量两包收编后两账 4 清单页共享 2 字节块（**真实数据去重 100%**）；scratch 卷真 docker plan 装机成功。**同案揪出更大的旧伤**：exportBundle 与重跑检测路由都拿"包目录"当平铺目录喂 scanBundle，而目录里只有 tar——**审计检测库恒 scanned:0，管理员的"检测无异常"是假绿**（skipped 其实一直诚实报数，没人看）。判例 54 的教训在此重演：**修存储形态要顺手核查每个读它的人**。测试面自撞三发：等长篡改才走到哈希关、空清单也要查目录存在、`const tar=路径` 恒真要 existsSync——都是"truthy 字符串当存在性"的同一族坑。
