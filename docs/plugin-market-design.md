## 1. 背景与目标

### 1.1 用户故事

- 作为**租户用户 A**，我在本地写好一个插件（不碰容器），希望在 Web 上几步把它**共享**给平台其他人。
- 作为**租户用户 A'**，我在自己容器的 DSH 里自写了插件（文件已在容器内），希望**直接共享**而不用重新上传。
- 作为**租户用户 B**，我登录 Web 后进入「市场」，可以**同时浏览技能与插件**，预览插件代码全文，**一键安装**到自己容器——运行中的 DSH 热生效（不重启容器），停着的容器下次启动生效。
- 作为**租户用户 B'**，我自己装过的东西（市场装 / 导入 / 容器内自写 / 外部下载）能在界面上一眼**分辨来源**，且知道哪些平台可管（卸载/更新）、哪些平台只读不动。
- 作为**维护者（admin）**，我在管理面板统一查看技能/插件的共享记录、下架可疑内容。

### 1.2 目标

| 目标           | 说明                                                                        |
| -------------- | --------------------------------------------------------------------------- |
| 统一市场       | 导航/页面/文案由「技能市场」更名为「市场」；技能与插件在同一页面按 tab 浏览 |
| 插件共享闭环   | A 发布 → 宿主共享仓 → Web 列表/预览 → B 安装 → B 容器 DSH 热挂载            |
| 与技能链路同构 | 复用签名挑战、共享仓、安装记录、配额、限流、下架整套机制，对称实现          |
| 来源可判别     | 四种安装途径 + 两条管理边界；宿主记账 / 配置树枚举 / 文件扫描三表对照       |
| 可审计         | 每条共享记录携带分享者、时间、文件哈希，admin 可下架                        |
| 热生效         | 安装/卸载通过 DSH 的补丁 HMR 热挂载/热卸载，见 §3 可行性结论                |

### 1.3 非目标（P1/P2）

- 多文件/zip 插件（含 `resources`、多入口）。MVP 为**单文件插件模块**（见 §4 理由）。
- 插件依赖第三方 npm 包（仅允许纯 JS、不依赖外部包，或只依赖 DSH 安装自带包）。
- 版本化、点赞/评分/评论。
- 全局共享挂载卷形态（所有容器共享一个插件根 + `customPluginDirs`，尚无此 DSH 配置面）。

### 2.1 两个关键事实（决定方案形态）

1. **DSH 用户补丁层是热更新的**：每个 profile 启动都会 watch `$DSH_HOME/profiles/web/cordis.patch.yml`
   （`@deepseek-ai/dsh-app-boot` 的 `watchUserPatches`）。补丁文件变化 → include `refresh()`
   → loader 树 `group.update()` **事务性**创建/更新/删除条目（已核对 `vendor/include` 与
   `vendor/loader/src/config/group.ts`：新条目热挂载、删除条目热卸载、失败回滚保持旧树）。
   → **往该文件追加一条 `insert`，运行中的 DSH 会热挂载新插件，无需重启容器。**

2. **加载器条目 `name` 支持 `file://` URL 与裸 npm 包名**：DSH 自身 e2e 测试即用
   `name: pathToFileURL(...).href` 挂载一个 `plugin.mjs`；裸包名则从配置目录（profile 目录）
   起按 Node 常规 node_modules 解析。→ **一个单文件插件模块即可成为合法条目**，
   写进租户卷即可被解析加载。

## 3. 可行性验证（DSH 源码核对结论）

| 问题                                       | 结论                                                                                                                       | 依据                                                                                             |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 改补丁文件能热挂载**新**条目吗？           | 能。`include.refresh()` → `root.update(data)` → `group.update()` 对每个条目 `create`、对消失条目 `remove`，事务性          | `vendor/include/src/index.ts:301`、`vendor/loader/src/config/group.ts:59-106`                    |
| `insert` 条目可以是文件 URL 吗？           | 可以。loader 对非 `cordis:` 的 `name` 直接 `import()`；`file:`/相对路径按配置目录解析                                      | `vendor/loader/src/config/tree.ts:145-159`；`apps/cli/tests/built-bin.e2e.ts` 用 file URL 挂插件 |
| 用户补丁层被 watch 吗？                    | 是。profile 与 home 级 `cordis.patch.yml` 都由 `watchUserPatches` 热监听（app 层的组合闭包）                               | `apps/cli/src/profile-boot.ts:285-290`（`watchUserPatches`）                                     |
| **容器内配置树可被读取吗（来源真相源）？** | 可以且无需 API——`profiles/web/package.json`（`dsh.profile.bundles`）与 `cordis.patch.yml` 都是卷内普通文件，辅助容器直接读 | §5.4 三表对照方案的前提                                                                          |
| 写卷操作是否需要改 DSH/镜像？              | 不需要。全部是"往租户卷写文件 + 改卷内补丁文件"，复用现有辅助容器通道                                                      | —                                                                                                |
| 容器停止时安装怎么生效？                   | 卷持久化；下次启动 `dsh --profile web --patch …` 启动时按已有补丁文件直接加载                                              | Dockerfile CMD；profile 补丁在启动即应用                                                         |

**结论**：插件安装 = (a) 把插件模块文件写进租户卷约定的插件目录 + (b) 把一条 `insert` 追加到
`/dsh-home/profiles/web/cordis.patch.yml`。两者都在辅助容器内完成，DSH 侧零改动。

## 4. 插件共享物形态：单文件插件模块（MVP，与技能对偶）

技能 MVP 的共享物是**单个 SKILL.md**；插件 MVP 对偶地取**单个插件模块文件**：

- 容器约定目录：`/dsh-home/profiles/web/plugins/<name>/index.mjs`（`<name>` kebab-case，
  **禁止路径穿越**；固定子目录避免与 `node_modules` 混淆）。
- 文件内容：ESM/CJS 模块，**default export 一个 Cordis 插件**（函数式 `({inject, apply})` 或
  `Service` 子类），与 `built-bin.e2e.ts` 里 `plugin.mjs` 示例一致。
- 挂载条目：

  ```yaml
  - insert:
      - id: plugin-<name>
        name: 'file:///dsh-home/profiles/web/plugins/<name>/index.mjs'
        config: {}
  ```

- 同一发布者重发同名 = 覆盖更新（连文件带条目）；他人占用同名 = `ConflictError`（与技能一致）。
- 文件级约束：≤ 64 KB；**必须通过 `node --check` 语法预检**（宿主侧对上传/提取内容先校验，
  防止写坏文件导致该租户 DSH 加载条目失败——loader 对失败条目是事务回滚，但会给日志留噪音）。

> 为什么不做 npm 包安装（`dsh plugin --profile web add <pkg>`）：需要租户容器访问 npm registry、
> pnpm 装依赖、node_modules 全量复制，重且不可控；单文件 + file URL 与现有辅助容器通道完全匹配，
> 且 P1 可无缝升级到"多文件包 + bundle patch"形态（`dsh.bundle` 声明本可直接复制进卷）。

### 4.1 插件来源（发布侧，两条通道）

1. **卷内约定目录**：与技能同构——`list-plugins.mjs` 扫描 `/dsh-home/profiles/web/plugins/`
   下合法目录名，`extract-plugin.mjs` 取回 `index.mjs` 内容 → "共享弹窗"选择发布。
2. **Web 导入**：UserCenter「我的插件 → 导入」：粘贴插件代码或上传单个 `.mjs/.js/.cjs` 文件
   → 宿主校验（名称、大小、语法、默认导出存在性嗅探）→ 签名 → 写卷 + 记 `source:'import'`
   → 同屏「共享到市场」。

两个来源的产物都是"卷内 `/dsh-home/profiles/web/plugins/<name>/index.mjs`"，发布前构造
`extract+validate` 流程，与技能 publish（卷提取）完全同构。

**共享语义（回答"用户如何共享自己的插件"）**：

- 共享 = **签名声明**：「这是我写的、我同意共享」。平台不验证"你是不是真作者"（作者身份
  测不到，见 §5.4），签名声明就是产品语义；策略上先发后审（admin 下架兜底），与技能一致。
- 提取源是**卷内文件**，所以无论哪条通道，最终都是"文件在卷约定目录里 → extract → 校验 → 入仓"：
  - Web 导入（**主通道**，插件常写在容器外）：粘贴/传 `.mjs` → 写卷（标记 import）→ 同屏一键「共享到市场」。
  - 容器内自写（**次通道**）：文件放进约定目录 → 共享弹窗列出（无标记=自写）→ 签名提取入仓。
    **注意**：放目录 ≠ 被 DSH 加载（加载靠补丁条目）；共享只读文件即可，不用先挂载。
  - 变体（链路现成）：download 现有插件文件 → 上传到另一地址 → 再共享。
- MVP 边界：只能共享**单文件插件**；多文件/包形（npm 包、带资源、`dsh.bundle` patch）→ P1。
  因此外部 npm 下载的多文件插件 MVP 不能一键转共享；单文件外部插件放入约定目录即可共享。

## 5. 数据模型

### 5.1 共享仓布局

```
data/
├── skills/                    # 既有技能仓（不动，向后兼容）
│   ├── index.json
│   └── <skillName>/SKILL.md
├── plugins/                   # 新增插件仓
│   ├── index.json             # 全量元数据（原子写）
│   └── <pluginName>/
│       └── index.mjs          # 插件模块原文（预览/安装来源）
└── installs.json              # 安装记录：记录增加 kind 字段（兼容旧记录：缺省视为 skill）
```

### 5.2 插件元数据条目（plugins/index.json 数组项）

| 字段          | 类型   | 必填 | 说明                                                         |
| ------------- | ------ | ---- | ------------------------------------------------------------ |
| `name`        | string | 是   | kebab-case，`/^[a-z0-9]+(-[a-z0-9]+)*$/`，= 目录名           |
| `description` | string | 是   | 市场卡片展示（插件类共享物无 frontmatter，发布时由用户提供） |
| `entry`       | string | 是   | `index.mjs`（MVP 固定；预留多文件扩展）                      |
| `sharer`      | string | 是   | 发布者 SWTC 地址（小写）                                     |
| `sharedAt`    | string | 是   | ISO 时间                                                     |
| `contentHash` | string | 是   | 文件 SHA-256（溯源/更新比对）                                |
| `bodyBytes`   | number | 是   | 文件字节数（配额/风控）                                      |
| `status`      | enum   | 是   | `active` / `removed`                                         |
| `kind`        | string | 是   | `'plugin'`（统一列表区分类型）                               |

> 技能条目不需要加 `kind`（技能仓独立）；**统一列表**在服务层合并时打标即可。

### 5.3 安装记录（installs.json，向后兼容）

```jsonc
// { <address>: [ { name, kind?, source, installedAt, contentHash, size } ] }
// kind: 'skill'（缺省=旧记录视为 skill）| 'plugin'；source: 'market' | 'import'
```

### 5.4 来源判别：四种安装途径的分类与处理

**术语澄清**：本平台市场本身也走网络传输，但传的是**我们共享仓的产物**；"直连互联网下载"
指不经本平台的直连方式（npm/github 等）。两者必须分开。插件实际存在**四种安装途径**：

| #   | 途径                                                                                              | 经手本平台？ | 容器内落点形态                                                                | 宿主 `installs.json` | 容器内标记文件 |
| --- | ------------------------------------------------------------------------------------------------- | ------------ | ----------------------------------------------------------------------------- | -------------------- | -------------- |
| 1   | **直连互联网下载**（如 `dsh plugin add <npm包>`、下 tarball 解压、手放 node_modules + 改补丁）    | 否           | `profiles/web/node_modules/<pkg>/`、npm 包名补丁条目、任意路径 + 自定义补丁行 | 无记录               | 无             |
| 2   | **本平台市场安装**                                                                                | 是           | `profiles/web/plugins/<name>/index.mjs` + `id: plugin-<name>` + file URL 条目 | `source:'market'`    | 有             |
| 3   | **Web 导入后安装**                                                                                | 是           | 与 #2 相同落点（标记 `source:'import'`）                                      | `source:'import'`    | 有（import）   |
| 4   | **容器内 DSH 自写/自挂**（模型经 `tool-cordis` 运行时挂载、或用户在容器里手写文件+补丁/临时挂载） | 否           | 任意：平台目录、node_modules、运行时挂载（loader 内存树，甚至不落盘）         | 无记录               | 无             |

**核心处理原则——两条管理边界（比"四种来源"更关键）**：

- **平台可管理（#2 #3）**：落点固定（`…/plugins/<name>/`）+ 标记文件 + 补丁 id 前缀 `plugin-` +
  `installs.json` 记录 → 平台**有完整痕迹**，才能提供卸载/更新/「本地已修改」判别/下架联动。
- **用户自管（#1 #4）**：平台**没有可靠痕迹**（文件可能在任何位置、甚至不落盘）→ 平台只做
  **只读**（卷扫描时展示为"外部/自写"、可提取去共享），**绝不自动卸载/覆盖/删除**；
  同名冲突时需用户明确确认并备份。

**扫描时的判别算法**（`list-plugins.mjs` 逐目录/逐条目）：

```text
有标记文件(.dsh-source.json) 且 installs.json 记 source=market   → 「市场安装」(可管理)
有标记文件 且 source=import                                      → 「导入」(可管理)
无标记文件 且位于平台管理目录 profile/web/plugins/<name>/       → 「容器内自写」(只读)
无标记文件 且 npm 包形态/条目为 npm 名/非平台目录                → 「外部下载或自装」(只读)
```

**处理规则明细**：

| 操作      | #1 外部下载                      | #2 市场安装                                  | #3 导入  | #4 容器内自写                |
| --------- | -------------------------------- | -------------------------------------------- | -------- | ---------------------------- |
| 卸载      | 不提供（平台无痕迹）             | `remove-plugin.mjs` 精确删自己条目+目录+标记 | 同左     | 不提供                       |
| 更新      | —                                | 重装覆盖（有标记，直接覆盖）                 | 同左     | —                            |
| 同名冲突  | 用户确认+备份                    | 重装：直接覆盖                               | 同左     | 用户确认+备份（`.bak-<ts>`） |
| 共享/发布 | 可（提取只读，用户签名声明作者） | 可                                           | 可       | 可                           |
| UI 呈现   | 「外部/自装」+风险提示           | 「市场安装」                                 | 「导入」 | 「自写」                     |

**编辑/更新歧义处理**（内容哈希三态，仅对 #2/#3 有效——平台有 `installedHash` 可对比）：

| 容器内文件 hash vs 标记 `installedHash` | 市场条目 hash vs 标记 `installedHash` | 判定                           | UI 呈现        |
| --------------------------------------- | ------------------------------------- | ------------------------------ | -------------- |
| 相等（未动）                            | 不等（市场上架了新版本）              | 市场有更新，安装的副本未动     | 「有更新」     |
| 不等（本地被改）                        | —                                     | 用户自己改过副本（不再是原样） | 「本地已修改」 |
| 相等                                    | 相等                                  | 与市场一致                     | 「已安装」     |

**覆盖边界与补强：以"配置树"为容器侧唯一真相源**

判别不只依赖"我们写过的标记"——`list-plugins.mjs` 同时**直接读容器内配置树的现实状态**：

```text
① profiles/web/package.json 的 dsh.profile.bundles   ← 外部 npm 包安装后会列在这里
② profiles/web/cordis.patch.yml 的全部条目            ← 含用户自己写的、非我们管理的条目
③ 平台管理目录 + 标记文件扫描                        ← 我们经手的痕迹
```

三表对照（installs.json 记账 / 配置树枚举 / 文件扫描）就能把**已持久化**的四类安装基本全部枚举：

| 观察结果                                                          | 判定                        | 可管理 |
| ----------------------------------------------------------------- | --------------------------- | ------ |
| ①/② 中存在我们管理的条目（`id: plugin-<name>` + file URL + 标记） | 市场安装/导入               | 是     |
| ② 存在非我们条目（npm 包名 / 自定义 id / 任意路径）+ 无标记       | 外部下载/自装               | 只读   |
| ① 的 bundles 里出现未记录包                                       | 外部下载                    | 只读   |
| ③ 存在但 ②/① 均无对应条目                                         | 自写（已卸/未挂，文件残留） | 只读   |
| 文件、配置树均不可见（仅运行时内存态）                            | 会话级临时挂载              | 只读   |

**真正测不到的两个残余（如实标注，不做无依据断言）**：

1. **运行时临时挂载**（如 `tool-cordis` 在 loader 内存树里挂、不落盘）——重启即消失，天然是
   "本次会话的临时物"，平台如实标注「会话级/临时」；P1 可用容器内 RPC（复用 `check-rpc.mjs`
   通道）探测运行中 DSH 实际装载的插件。
2. **手改到无法辨认**（改名/移走/改内容）——这是"作者身份"问题，任何系统都无法证明
   "这串代码是不是你写的"；平台只承诺**痕迹记账 + 只读边界**：我们经手写下的痕迹我们负责
   管理，没有痕迹的一律视为用户自管、绝不擅动。

> 结论修正：不是"无法涉及所有情况"，而是**持久化状态可全覆盖**（配置树是容器内唯一真相源），
> 只剩两类"诚实上报"的残差——会话级临时挂载、以及任何人无法证明的"作者身份"。

**技能侧差异**：DSH 技能只有"写文件到 `/dsh-home/skills/`"一种进容器方式，没有 #1
（npm 安装）形态，故技能只有三途：市场 / 导入 / 自写，同一套标记与只读边界适用。

## 6. API 设计（镜像 /api/skills/_，前缀 /api/plugins/_）

统一前缀 `/api/plugins`，挂进 `server.js`（在 skills 分支旁新增）。鉴权分层与技能完全一致：
公开 GET（列表/详情/下载）、钱包签名（publish/import/install/uninstall/mine/DELETE）、admin cookie（admin/hide）。

| #   | 方法/路径                           | 鉴权           | 说明                                                                                                                            |
| --- | ----------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `POST /api/plugins/challenge`       | 无（地址合法） | **共用技能 nonce 池**（同 `tenantConfigService.issueChallenge`）                                                                |
| 2   | `GET /api/plugins?address=`         | 无             | 市场列表（active，含 installed 标记）                                                                                           |
| 3   | `GET /api/plugins/:name`            | 无             | 详情 + **代码全文预览**（安装前必看）                                                                                           |
| 4   | `POST /api/plugins/publish`         | 钱包签名       | body `{address, pluginName, description, nonce, signature, publicKey}`；先从该地址卷提取插件代码 → 校验（语法/大小/导出）→ 入仓 |
| 5   | `POST /api/plugins/import`          | 钱包签名       | body `{address, pluginName, content, nonce, …}`；校验后写自己卷 + `source:'import'`                                             |
| 6   | `POST /api/plugins/:name/install`   | 钱包签名       | 安装到自己卷：写文件 + 标记 + 追加补丁条目 + 记 `kind:'plugin'`；遇自写冲突回 `{conflict:'self-written'}`                       |
| 7   | `POST /api/plugins/:name/uninstall` | 钱包签名       | 删文件 + 标记 + 移除补丁条目 + 删安装记录（只删平台管理形态）                                                                   |
| 8   | `DELETE /api/plugins/:name`         | 签名或 admin   | 作者取消共享 / admin 代下架（不影响已装用户副本）                                                                               |
| 9   | `POST /api/plugins/:name/hide`      | admin          | 下架                                                                                                                            |
| 10  | `GET /api/plugins/mine?address=`    | 无（视图）     | 我的发布 + 我的安装（含来源徽标与三态）                                                                                         |
| 11  | `POST /api/plugins/mine`            | 钱包签名       | 追加容器内可共享插件列表（共享弹窗用，含 source 标注）                                                                          |
| 12  | `GET /api/plugins/admin`            | admin          | 全量管理视图（含 removed、安装数）                                                                                              |
| 13  | `GET /api/plugins/:name/download`   | 无             | 导出插件源文件（备份/本地搬运用）                                                                                               |

### 6.1 统一市场列表

```text
GET /api/market?kind=skill|plugin|all&address=
→ { ok, items: [ { kind:'skill', …技能字段 } | { kind:'plugin', …插件字段 } ] }
```

## 8. 安全设计（插件 = 可执行代码，比技能更需透明）

| 防线     | 措施                                                                                                                      |
| -------- | ------------------------------------------------------------------------------------------------------------------------- |
| 知情     | 安装前强制预览**全部插件代码**；卡片展示分享者/时间/哈希；插件卡片固定「⚠ 插件代码将在您的容器内以 DSH 进程权限执行」提示 |
| 来源     | 四途径判别（§5.4）：平台可管的展示「市场安装/导入」，用户自管的标注「外部/自写/会话级」并给风险提示                       |
| 溯源     | 每条共享记录含 sharer/sharedAt/contentHash，admin 可审计                                                                  |
| 处置     | admin 下架；`status=removed` 不可再安装；**已安装用户的副本不受影响**（各自容器独立）                                     |
| 语法闸   | 入仓/安装前 `node --check` 语法校验 + 默认导出嗅探，损坏文件不落卷                                                        |
| 边界声明 | 插件只运行在**安装者自己的容器**内（无跨租户执行面）；风险模型 = "安装他人软件"，透明预览 + 可卸载兜底                    |
| 滥用控制 | 发布 ≤20/地址、单文件 ≤64KB、安装限流每地址每小时 10 次（**与技能共用同一计数**，决策已定）                               |
| 扩展预留 | P2 支持"共享插件禁用网络/文件系统"需 DSH 侧策略能力，本期仅文案提醒                                                       |

## 9. 边界与错误处理

| 场景                                        | 行为                                                                                  |
| ------------------------------------------- | ------------------------------------------------------------------------------------- |
| 卷内无该插件                                | publish 报「容器内未找到插件 xxx」                                                    |
| 插件语法非法 / 无默认导出                   | 拒绝入仓/写卷，回显具体错误（`node --check` 输出）                                    |
| 发布占用他人同名                            | `ConflictError`：提示改名（插件侧无 frontmatter，改名=改目录名+文件名，直接 reroute） |
| 同一发布者重发同名                          | 覆盖更新（新 hash/time），已装用户列表标记「有更新」                                  |
| 容器不存在（B 从未创建/已销毁）             | 走既有语义：提示先连接钱包激活容器（写卷失败抛 InternalError）                        |
| 补丁文件被用户手改（含其他行）              | `patch-yaml.mjs` 只增删自己的 `insert` 条目，其余行原样保留；冲突 id 以最新写入为准   |
| 安装写文件成功、补丁更新失败                | 不记 installs；尽力回滚已写文件（删除目录与标记）；报错原因含补丁行                   |
| HMR 挂载失败                                | loader 事务回滚保持旧树；DSH 日志可见；下次容器重启仍按补丁文件重试                   |
| 导入 zip / 多文件                           | 提示「本期仅支持单个插件模块文件」（zip/多文件见 P1）                                 |
| 用户编辑了市场安装的副本                    | 容器内 hash ≠ 标记 `installedHash` → 显示「本地已修改」，不再提示「有更新」           |
| 同目录存在自写内容时再装市场同名            | 安装脚本返回 `conflict:'self-written'` → 前端确认后备份（`.bak-<ts>`）再覆盖          |
| 扫描到会话级临时挂载（配置树/文件均不可见） | 标注「会话级/临时」；列表正常展示但平台不提供任何管理操作                             |

## 11. 总验收标准

1. 导航与页面统一为「市场」，技能与插件同页双 tab 可浏览/搜索/预览/安装。
2. 用户共享自有插件两条通道均通：**Web 导入 → 共享**（容器外写插件场景）与**容器内自写 → 共享弹窗**（文件已在卷内场景），均签名发布、市场可见。
3. 用户 B 预览插件代码后签名安装 → 运行中的 DSH **热挂载**（不重启），停止的容器下次启动生效。

5. 每次安装/导入/发布有签名鉴权；路径无穿越；语法非法内容不落卷。
6. 既有技能市场全部功能与测试回归通过（`npm test`、`vite build`）。
7. **四途径来源判别成立**：任何容器内技能/插件都能标注来源（市场安装 / 导入 / 容器内自写 / 外部下载 / 会话级）；宿主记账、配置树枚举、文件扫描三表对照一致；**用户自管内容（自写/外部）不会被市场卸载、覆盖、删除**；哈希三态（有更新/本地已修改/已安装）展示正确。
